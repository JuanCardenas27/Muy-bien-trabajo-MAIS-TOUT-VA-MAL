# Operación diaria y puesta en marcha -- Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Lee `AGENTS.md` antes de tomar una tarea.

**Goal:** Que el pipeline corra solo cada mañana a las 05:17 America/Bogota desde el repo público de producción, guarde datos y estado en un bucket privado de Cloudflare R2, publique el bundle cifrado solo cuando haya algo nuevo, avise con un único issue sin contenido cuando algo falla, y dejar la puesta en marcha real (GCP, R2, Worker, secretos, backfill) como checklists que se hacen en el navegador.

**Architecture:** Cuatro comandos nuevos en `frances.ops` (`run-daily`, `report-failure`, `doctor`, `r2`), dos workflows de producción (`daily.yml`, `reconcile.yml`) que encadenan lease → `r2 pull` → `restore` → `run-daily` → `dump` → (si cambió algo) `bundle` + `r2 publish` → `r2 push` → `report-failure` si falló; un Worker de Cloudflare que sirve solo `site/` del bucket; Pages publica la app (solo código) y el demo sintético. Nada corre en el PC del usuario (R-30 g). Nada del Classroom entra al repo ni a sus logs.

**Tech Stack:** Python 3.12 + Typer, boto3 (API S3 de R2 con escrituras condicionales), `subprocess` con argv para `gh`, bash (`set -euo pipefail`), `jq`, GitHub Actions (`actions/checkout`, `astral-sh/setup-uv`, `actions/setup-node`, `actions/upload-pages-artifact`, `actions/deploy-pages`), Cloudflare R2 + Workers (wrangler, vitest), PyYAML + `tomllib` en los tests, shellcheck.

**Spec:** `docs/superpowers/specs/2026-10-14-frances-classroom-design.md` (D1, D2, D11, D12, §5, §6.9, §7, §8, §10)

Plan maestro: docs/superpowers/plans/2026-10-14-00-master-plan.md (Global Constraints y contratos aplican a todas las tareas)

## Restricciones del subsistema

- Toda action de terceros va fijada por SHA de commit de 40 hex con el tag como comentario (`uses: actions/checkout@<sha> # v4.2.2`). El SHA se resuelve al implementar con `gh api repos/<owner>/<action>/commits/<tag> --jq .sha` (resuelve también tags anotados); nunca un tag ni una rama.
- Secretos solo en el environment `production` del repo de producción (R-30), y solo los de la lista de variables de entorno del plan maestro (más `GITHUB_TOKEN`/`github.token`). Se exponen con `env:` a nivel de **step**, nunca de job ni de workflow, y solo al step que los usa. Nada de `set -x`.
- Los logs de Actions son públicos y no llevan contenido: ni títulos, ni nombres de curso, ni texto, ni mensajes de excepción sin redactar. Los comandos de este plan imprimen nombres de etapa, estados, conteos, hashes y tamaños; todo lo demás pasa por `frances.log.redact()`.
- El repo nunca ve datos reales: ningún archivo del Classroom se commitea, y los workflows con secretos (`daily.yml`, `reconcile.yml`) solo corren por `schedule` o `workflow_dispatch` en el repo de producción (`vars.FRANCES_PROD == 'true'`). `ci.yml`, `contracts.yml`, `e2e.yml`, `pages.yml`, `worker.yml` y `spike-voices.yml` no referencian ningún `secrets.*`. Prohibidos `pull_request_target` y runners self-hosted (R-30).
- Un solo escritor del bucket a la vez: `daily.yml` y `reconcile.yml` comparten `concurrency: {group: frances-prod, cancel-in-progress: false}`, y ambos toman el lease `locks/writer.json` de OPS-03. `state.sql` se sube con `If-Match`, así que un escritor que se coló nunca pisa el estado de otro.
- Exit codes: los del plan maestro. En los workflows, `2` (parcial) deja el job verde con un `::warning::` y no abre issue (spec §6.9: se reintenta al día siguiente; aceptado en R-25); `1` y `3` abren o comentan el issue y terminan el job con ese código.
- CLI (R-05): cada comando propio declara `data: DataOpt = Path(".")` (FND-04, `frances.cli`), arma el contexto con `make_context(data)` (FND-03, `frances.stage`) y termina con `exit_with(...)`; no hay `--data` global.

## Review Focus

El plan maestro no asigna ítems a P07. Del subsistema:

1. Una falla de auth no deploya un sitio vacío ni pisa el del día anterior: con exit 3 no se escribe nada, `changed` es `false` y los steps de build/bundle/deploy no corren. Tests: OPS-02 `test_auth_error_stops_pipeline_and_marks_unchanged`, OPS-05 `test_deploy_steps_skip_on_auth_failure`.
2. El issue de fallo nunca filtra contenido del curso: el cuerpo lleva solo nombres de etapa, estados, conteos enteros, el exit code y el enlace al run. Test: OPS-04 `test_issue_body_has_only_stage_status_and_counts`.
